STARTcloud Universal Validation

The picture of the Universal Validation Contract; where the two disagree, the contract's text wins. One rule set per UI backend, written once as JSON Schema keywords and read by the form and the write route alike, so a value cannot pass in the browser and fail on the server or the reverse. One place a field error is shown (beside its field), one place a form's errors are listed (the summary at its top), one body every UI backend answers when a write is refused (RFC 9457 Problem Details with an errors array of JSON Pointers), and one status per case: 422 when a value breaks a rule, 409 when it is already taken, 400 when the request could not be read. Cards, banners and toasts never carry a field error. The first frame is live: type in a field and leave it, submit the form empty, then use the three buttons under the form to see the same form after the server answers 422, 409 and a request-level failure.

What this frame proves. The same rule set evaluates in the browser and, simulated here, on the server; every failure lands beside its field with the same wording the summary links to, and nothing about a field ever appears as a card.
Changed: timing. No rule runs while the user types (NN/g guideline 7, GOV.UK); a field is checked when the user leaves it and every field is checked on submit. The box, version, provider and architecture forms checked the name on every keystroke and disabled Save; that goes.
Changed: no field error in a card. The org console, the admin organizations tab, the box and ISO slots and discovery raised field errors through notify(); those become inline errors and the summary. Cards keep what they had: the outcome of a request that was accepted or refused as a whole.
Changed: one error component. Six drawings (auth-field-error, text-danger, invalid-feedback, FormField, AuthAlert, cards) become FieldError and FormErrorSummary, drawn once in components/common.
Accessibility, on every field: aria-invalid="true" only after a blur or submit found it wrong (ARIA 1.2), the control's aria-describedby and aria-errormessage naming the error's id, the error text prefixed by a visually hidden "Error:" (GOV.UK), the summary role="alert" and focused on submit (WCAG 4.1.3, ARIA19), the input never cleared.

The wire — what the UI backend answers on a refused write, and how the UI reads it

422 Unprocessable Content · application/problem+json

HTTP/1.1 422 Unprocessable Content Content-Type: application/problem+json { "type": "https://auth.startcloud.com/probs/validation", "title": "The request did not pass validation.", "status": 422, "errors": [ { "pointer": "/name", "rule": "pattern", "params": { "pattern": "slug" }, "detail": "name must match slug" }, { "pointer": "/version_number", "rule": "minLength", "params": { "minLength": 1 }, "detail": "version_number must be at least 1 character" } ] }

409 Conflict · the one failing rule is unique

HTTP/1.1 409 Conflict Content-Type: application/problem+json { "type": "https://auth.startcloud.com/probs/conflict", "title": "The value is already taken.", "status": 409, "errors": [ { "pointer": "/name", "rule": "unique", "params": { "scope": "STARTcloud" }, "detail": "name is already used in STARTcloud" } ] }

400 Bad Request · the body could not be read

Changed: the password rule. NIST SP 800-63B rev 4 §3.1.1.2: minimum 15 for a single-factor password, at least 64 allowed, no composition rules, Unicode and spaces accepted, a blocklist on the server. The UI's 6–40 and the backend's upper/lower/number/symbol knobs go; the UI backend publishes its minimum and the UI's rule reads it.
Changed: the email rule. The WHATWG "valid e-mail address" grammar on both sides, one regex, replacing the three the UI carried and the check the backends did not do.
The auth pages keep their own column and typography but draw the same FieldError and FormErrorSummary; the AuthAlert stays for the page-level messages that are not about a field (a provider error, a closed registration).
