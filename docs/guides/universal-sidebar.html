STARTcloud Universal Sidebar

One sidebar for every UI backend that needs one, and none for the ones that do not. The manner is borrowed from hyperweaver: the column runs the full height of the viewport on the left, its top is the brand mark and the product name, a click there collapses it to a 38px rail and expands it again, and the navbar, the page and the footer sit to its right and move with it. The window never scrolls: the column's entries and the page each scroll inside themselves, and the footer stays the one fixed row. A feature fills the column by exporting entries, gated by the same tokens and roles that gate its routes; a UI backend with no entries keeps the sidebar-less chrome BoxVault and the catalog have today, with the brand in the header. Two entry kinds share one column: sections of links, the shape the authorization server's admin needs, and a live tree, the shape the fleet monitor's pools would take. The first frame is live: pick a UI backend, click the brand to collapse, scroll inside the column and the page.

Live — the same AppShell on the estate's UI backends; only the entries the mounted features export differ
What this frame proves. The column is the outer row's first cell and the whole header, page and footer stack is its second, so collapsing the rail pushes everything right in one motion; the cluster, the crumbs and the footer are otherwise untouched, and the column appears only when a feature registered entries. Sections and a tree are both entry kinds, so the auth server's admin, BoxVault's admin and the fleet monitor's pools draw through one component with one row style, one rail and one persistence.
Scroll. The frame is viewport-high and nothing outside it scrolls: the column's entries scroll in their own region under the brand, the page scrolls in the region between the header and the footer, and the footer is the one 13px row of the navbar contract, fixed, with no drawer.
Changed: the shell. `AppShell` becomes a row: `Sidebar` first when the `sidebar` prop carries entries, then the column of header, notices, scroll region and footer; with no entries the row has one cell and the layout is byte-identical to today.
Changed: the brand moves. With a sidebar the brand mark and product name are the sidebar's top and its collapse control; the header row then opens with the crumbs. Without a sidebar the header keeps the brand as today.
Changed: the foot is bare unless a feature exports `actionMenu`. Without the export there is no profile drop-up and no action strip: identity, organizations, favorites, notifications, help and logout stay in the header's user menu, a page's actions stay on the page, and the column ends at its last entry. With the export the swap below applies.
The swap. While any mounted feature exports `actionMenu`, the header's account slot draws that menu (the same toggle shape, a label and a glyph) and the user menu moves to the sidebar foot as a drop-up whose toggle is the identity card, the avatar alone in the rail. No flag: the export is the switch. Hyperweaver is the first fit, its scope-aware Controls (Machine, Host actions, Bulk actions) taking the slot; the frame shows it as the fifth backend.

Why the order matters. A later contract never restates an earlier one; it names the section it builds on. So a reader who starts at the identity contract meets the sidebar, the pages and the navbar by reference, and the shell is understood by reading them in the order above once.
Nothing is per app. Every row of the assembled table differs only in what the UI backend's status answers and which features that answer mounts; the code paths are the same on both columns, and a third UI backend is a third column with no new code in the shell.

The auth server's entries. For every signed-in person, from the profile feature: Account: Profile, Organizations, Integrations, Inbox (the unread badge from the `notifications` topic). For an admin, from the identity feature's own operator export below it, mounted by the `cookie` token and never a role branch inside the shared admin feature: Overview: Dashboard. Accounts: Users, All organizations. Activity: Logins, Registrations, Sessions. Health: Service usage, Insights, Client health. Security: Blocked IPs (the badge from the `admin` topic's `blocked-count`). Content: Terms. System: Configuration. A person's pages are the whole of the issuer, so the column draws for everyone; the rows are the one navigation, and no page repeats them as a tab strip under its header. The user menu on the issuer carries no Admin and no Preferences row, since Dashboard and Profile are rows here; the column is hidden on the sign-in, onboarding, interstitial and error routes.
BoxVault's entries. The shared admin feature exports on every UI backend that advertises `admin`, each entry only while the adapter carries `organizationsWithUsers`, `config` or `storage`, so BoxVault's admin page splits into Organizations and users, Configuration and System rows; its box and ISO pages export nothing, and on the issuer, whose adapter carries none of the three, the shared feature exports nothing.
When the sidebar shows. On every page once a feature exported entries, BoxVault's admin group beside its box pages included; a user who wants it out of the way collapses it and `sidebar_minimized` remembers, hyperweaver's manner.
Views on a tree. A tree may export more than one shape and a select at its top switches between them, Proxmox's manner: VDI Health offers by pool, by host and by session state, the same VMs under different parents; the open nodes are kept per view.
Entries only from features. `/api/status` adds no links today; an ad-hoc link source is a later addition, not a rule against it.
