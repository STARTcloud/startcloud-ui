## Universal Testing Contract

{: .no_toc }

The testing contract: the one browser test tool for the estate and the reusable workflow every UI
backend calls, where tests live per repository class, what every UI backend must prove per
contract checklist, and the fixtures. Tests are uniform and convergent across the family because
one tool and one workflow run them, and no repository carries a hand-written smoke script of its
own. Every file this contract adds to the shared UI is JavaScript, never TypeScript, and no test
reads a `.env` file: the environment is what the workflow or the shell sets.

## Principles

- **One tool, one workflow.** Tests are uniform and convergent across the family because one
  tool and one workflow run them. Why: a second tool or a second workflow shape is a second thing
  to keep identical across the family.
- **Tests are tools, never scripts.** No workflow carries a hand-written smoke script; a check
  that must survive becomes a proper tool in a reusable workflow, never an ad-hoc script. Why: a
  curl script encodes assumptions nobody maintains and diverges per repository.
- **The browser test tool is a normal step of the standard `ci.yml`.** The same shape in every
  repository of its class; Playwright. Why: the same workflow file names and shapes, copied not
  written.
- **Gherkin on frontends, live instances on backends.** Cucumber or Gherkin style on frontends;
  live-instance tests rather than mocks on backends.
- **100 percent is the aim.** Coverage is measured on every run and the aim is 100 percent; a
  branch coverage cannot reach is listed under `uniformity.potential_dead_code` with the reason it
  is unreachable, so it can be removed or the guard above it moved, never tested around. Why: a
  branch stays only while a caller can reach it.
- **A checklist line reads ✓ only when the backend's own tests assert it.** Owed while its change
  list names the row; n/a where the rule has nothing to bind. Why: a tick without an asserting
  test is a claim, not a proof.
- **The shared UI proves its contracts over a fixture, never a dev proxy target.** The shared UI
  carries a test fixture of the config and setup routes under this contract's runner. Why: a test
  that needs a running backend is a test that runs only on one developer's machine.
- **Tests follow the contracts, they do not lead them.** A proof asserts a line of an existing
  contract's checklist; a rule that matters is written in its contract first. Why: the contract
  drives the code.

## 1. The one tool

| Rule                | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Why                                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| the browser tool    | one browser test tool for the estate, Playwright; it is a normal step of each repository's standard `ci.yml`, the same shape in every repository of its class; no repository runs a second browser tool; the shared UI's `playwright.config.js` is JavaScript and reads `process.env` alone, no `.env` file and no `dotenv`                                                                                                                                                                                                                             | one tool is what makes the tests uniform and convergent                        |
| the Gherkin layer   | Cucumber or Gherkin style on frontends: every browser test of the shared UI is a `.feature` file of scenarios in Gherkin, run through `playwright-bdd`, which generates Playwright tests from the features so one runner runs them and one report shows them; a step is written once in a step file and reused by every scenario that says the same thing                                                                                                                                                                                               | a scenario reads as the contract line it proves                                |
| the unit runner     | one unit runner per class: Vitest for the shared UI's `schemaSections`, `validation`, `useFormRules`, `ConfigPage` and `SetupPage`; Jest 30 with supertest for the Node backend; pytest for the Python backend; the Java backend's Gradle test task; Vitest with Cloudflare's Workers pool for the Worker; each named once in section 2 and never a second one in the same class                                                                                                                                                                        | one runner per class is the same-shape rule applied to the unit layer          |
| live instance       | on a backend a test runs against the backend's own process booted from the module's own configuration resolution, the config contract's development directory or a `CONFIG_DIR` the test job sets, over a real database of the class's test dialect; nothing the route reads is mocked; how the instance is stood up per class is section 5; the unit layer keeps the in-process app under a request library (BoxVault's supertest over the Express app), and the browser scenarios run against the process listening on a port as `npm start` boots it | a mock proves the mock                                                         |
| coverage            | every unit and live-instance run reports coverage through the runner's own coverage reporter; 100 percent is the aim; a branch no request can reach is listed under `uniformity.potential_dead_code` with the reason and is never tested around; coverage is reported on every run and uploaded with the report and gates nothing until a class reaches its first figure, when that figure becomes its floor and never moves down                                                                                                                       | the aim and the `potential_dead_code` rule                                     |
| no smoke script     | no workflow of any repository carries a hand-written smoke script: no inline `curl`, no inline `node --input-type=module`, no `python -c` that asserts a route; a check that must survive becomes a test under the runner of section 2 or a step of the reusable workflow of section 3; the shared UI's locale parity is the unit test `tests/unit/localeParity.test.js`                                                                                                                                                                                | a curl script encodes assumptions nobody maintains and diverges per repository |
| the screenshot      | every conformance-checklist line is ticked with a side-by-side screenshot in the PR; the browser tool keeps a screenshot, a trace and a video of every failing scenario and uploads them with the run's report as a workflow artifact, and the PR screenshot stays until the line's scenario passes                                                                                                                                                                                                                                                     | a tool that already drives the page can capture it                             |
| what a test asserts | a test asserts one line of one contract's conformance checklist, named in the test's title in the checklist's own words; a test that asserts no checklist line is a unit test of one function and is titled by that function                                                                                                                                                                                                                                                                                                                            |                                                                                |

## 2. Where tests live per repository class

The classes: the shared UI, a Node backend (BoxVault, hyperweaver-server, zoneweaver-agent), a
Python backend (the VDI Health Monitor), a Java backend (the authorization server), a Worker (the
provisioner catalog).

| Class          | Directory                                                                                                                                                              | Naming                                                                                                                                                                                        | Fixtures                                                                                                                                                                                                                 | Runner                                                                                                                                                                     | Why                                                                                                                                      |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| shared UI      | `tests/` at the repository root: `tests/features/` for the `.feature` files and their step files, `tests/unit/` for the unit tests, `tests/fixtures/` for the fixtures | a feature file per contract, `<contract>.feature` (`config.feature`, `validation.feature`); a step file beside it, `<contract>.steps.js`; a unit test per module it tests, `<module>.test.js` | `tests/fixtures/<contract>/index.js` keyed `"METHOD path"`, one JSON file per answer beside it (section 5)                                                                                                               | Playwright through `playwright-bdd` for the features; Vitest for the unit tests; both as `npm` scripts beside `lint`, `format:check` and `quality`, the CONTRIBUTING chain | the feature-first tree of CONTRIBUTING and the pages contract keeps tests out of `src/`                                                  |
| Node backend   | `backend/tests/`; a backend whose code is at the root uses `tests/`                                                                                                    | `<subject>.test.js`                                                                                                                                                                           | `backend/tests/__test_config__/` holding one `<name>.config.yaml` per name in `status.config`, written by the runner's global setup and handed to the process as `CONFIG_DIR`; the test dialect `sqlite` with `:memory:` | Jest 30 with supertest                                                                                                                                                     | the first backend of the class holds the shape and every later backend copies it, the config contract's one-module rule applied to tests |
| Python backend | `tests/` at the repository root                                                                                                                                        | `test_<subject>.py`                                                                                                                                                                           | a test configuration directory of one `app.config.yaml`, handed as `CONFIG_DIR`, the Python twin of the Node backend's `__test_config__`                                                                                 | pytest, installed from `requirements-dev.txt` beside `ruff` and `pip-audit`                                                                                                | the same shape as the Node class in the language's own convention; `requirements-dev.txt` is where the class keeps its tools             |
| Java backend   | `src/test/groovy/<package>/`                                                                                                                                           | `<Subject>Test.groovy`                                                                                                                                                                        | the test resources beside the tests; the boot test reads `application.config.yaml` from a test `CONFIG_DIR`                                                                                                              | `./gradlew test`                                                                                                                                                           |                                                                                                                                          |
| Worker         | `worker/tests/`                                                                                                                                                        | `<subject>.test.js`                                                                                                                                                                           | the Worker's `[vars]` for the test run; no configuration files                                                                                                                                                           | Vitest with Cloudflare's Workers pool; the live Worker is `wrangler dev` on the runner                                                                                     | a backend with no files has no `CONFIG_DIR` to hand over; its test shape is its platform's                                               |

The browser scenarios are the shared UI's alone, over its fixture; no backend writes a `.feature`
file or runs the browser tool, because the backends' proofs are their own unit and live-instance
tests under the runner of their class.

## 3. The reusable workflow

| Rule              | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Why                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| one workflow      | one reusable workflow in this repository, `.github/workflows/tests.yml` with `on: workflow_call`; every UI backend calls it from its standard `ci.yml` as a job with `uses: STARTcloud/startcloud-ui/.github/workflows/tests.yml@main`; the ref is `main`, because the workflow's shape moves with the contract and a caller pinned to a tag would carry a second pin beside `startcloudUiVersion` for a file that ships no code                                                                                                                                                                                                                                                   | one workflow is what makes the tests convergent; a workflow copied into each repository is five workflows       |
| what it does      | checks out the caller, sets the class's language up, installs its dependencies, fetches the pinned UI release into `ui/` (`curl -fsSL … \| tar -xz -C ui`, the navbar contract's Distribution section), builds the shared UI, runs the class's unit command, and for the shared UI alone installs the browser tool's Chromium with its system dependencies and runs the features; a caller that names a `boot` command has its live instance booted in the background and awaited on `GET /api/status` before its unit command runs (section 5); the report, the failure screenshots, traces and videos, the coverage and the instance's log are uploaded as one workflow artifact | the steps every class shares are the workflow's; what differs per class is an input                             |
| inputs            | `class` (`shared-ui`, `node`, `python`, `java`, `worker`), `runs-on` (`ubuntu-latest`), `node-version` (`22`), `python-version` (`3.11`), `java-version` (`25`, `temurin`), `working-directory` (`.`), `ui-version` (the pinned release to unpack, passed by the caller from its own pin location, empty for the shared UI), `config-dir` (the `CONFIG_DIR` the live instance boots from), `boot` (the background command, empty for a class whose unit runner boots its own app), `origin` (`http://127.0.0.1:3000`) and `unit` (the class's unit command); no input carries a secret                                                                                             | the caller says what it is and the workflow does the rest; a secret in an input is a secret in a log            |
| the standard step | in every repository of a class the calling job is named `tests`, titled Tests, carries the same inputs, copied not written, so `ci.yml` differs between two Node backends only in the values of its inputs; CodeQL `needs` it beside lint and build; the job runs on every pull request and on the push to `main` through `release-please.yml`'s `ci-checks` job                                                                                                                                                                                                                                                                                                                   | the same shape in every repository of its class                                                                 |
| no smoke script   | the workflow carries no `run:` step that asserts an answer; every assertion is in a test file under the runner                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |                                                                                                                 |
| private callers   | the authorization server, the VDI Health Monitor and the private catalog are private repositories and call the public workflow; the workflow runs on the caller's runner, so the authorization server's job passes `runs-on: self-hosted` and keeps its runner, and the browsers are installed by the workflow's own step on every run there too, because a runner prepared by hand is a runner nobody can rebuild                                                                                                                                                                                                                                                                 | a private repository may call a reusable workflow of a public one; the caller's runner is where its checkout is |
| CodeQL            | the shared UI, BoxVault and the catalog chain `codeql.yml` after their checks; private repositories do not get CodeQL                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |                                                                                                                 |

## 4. What every UI backend proves

One proof per line of every contract's conformance checklist. A proof is a test that asserts the
line and is titled by it; a backend proves its lines against its live instance, the shared UI
proves its lines over the fixture of section 5, and a line that needs the browser is a Gherkin
scenario run by the browser tool. The lines are the checklists' own; a checklist that grows a line
grows a proof.

## 5. Fixtures

| Rule                         | Value                                                                                                                                                                                                                                                                                                                                                                                                                                    | Why                                                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| the shape                    | `tests/fixtures/<contract>/index.js` exports one object keyed `"METHOD path"` (`'GET /api/status'`, `'PUT /api/config/app'`), each value `{ status, file }` naming the JSON file beside it, and `refused` naming the file a refused write answers; a fixture file is the contract's own example body, so `put-422.json` is the config contract's refused write verbatim                                                                  | one key names one answer; a fixture that is the contract's example cannot drift from it                           |
| the config fixture           | `status.json`, `app.config.json`, `app.schema.json`, `put-200.json`, `put-422.json`, `restart-status.json`, `upload-200.json`, `setup-status.json`, `setup.json`, `setup-schema.json`; every contract's fixture takes the same layout under its own folder                                                                                                                                                                               | the first fixture is the shape                                                                                    |
| how it is served             | the browser tool intercepts every `/api/*` request the shared UI makes, `tests/features/support/fixtures.js`, and answers the fixture's file with its status from the `"METHOD path"` key, a key the fixture lacks answering 404 with a problem body; the shared UI is never pointed at a dev proxy target for a test; the scenarios run over the built `dist/` served by `vite preview`                                                 | never a dev proxy target; the dev server proxies `/api` to a target and the build is what every UI backend serves |
| a refused write              | a scenario that sends a bad value receives `refused` with its status; the test asserts the surfaces the validation contract fixes, painted by pointer                                                                                                                                                                                                                                                                                    | the validation contract's Surfaces table                                                                          |
| a backend's live instance    | per class, the process booted as its `ci.yml` builds it: the Node backend with `CONFIG_DIR` at its `__test_config__` written by the runner's global setup and `database_type: sqlite` over `:memory:`; the Python backend with `CONFIG_DIR` at its test directory; the Java backend under `./gradlew test` with a test `CONFIG_DIR`; the Worker under `wrangler dev`; the pinned UI tarball unpacked into `ui/` before the process boots | the config contract's one-variable rule makes `CONFIG_DIR` the whole test setup                                   |
| the test dialect             | a Node backend runs `sqlite`; a branch reachable only on MySQL stays listed under `potential_dead_code` until a MySQL run exists; the workflow adds no MySQL run until the class's first run is green on `sqlite`                                                                                                                                                                                                                        |                                                                                                                   |
| the browser and the backends | no backend runs the browser tool; the browser scenarios are the shared UI's over its fixture, and a backend proves its lines with its own unit and live-instance tests under the runner of its class                                                                                                                                                                                                                                     | the backends' tests are theirs                                                                                    |
