STARTcloud Universal Config

The picture of the Universal Config Contract; where the two disagree, the contract's text wins. Every backend keeps its settings in plain YAML files an administrator can read and edit, api_listen_port_encrypted: 443, and ships beside its code one schema per file that says what every value is, what it may be, how it is drawn and whether changing it needs a restart. The schema is the validation contract's rule set, JSON Schema 2020-12 keywords, so the admin page, the setup page and the write route evaluate one document and refuse a bad value the same way with the same body. Two environment variables, CONFIG_DIR and the environment switch, and no more. The first frame is live on the VDI Health Monitor, the one-file UI backend: set a check-in interval past its maximum, clear the origin and press Update, then let the UI backend answer 422 for a value the browser could not know was wrong.

a yellow note marks what this design changed against the apps as they were before it
Live — the VDI Health Monitor's Configuration tab: app.config.yaml drawn from its schema, validated on blur and on Update, the PUT's 422 painted by pointer, the restart badge from requiresRestart
What this frame proves. Two documents, one form: the values come from GET /api/config/app, the labels, hints, types, bounds and enums from GET /api/config/app/schema, and the route evaluates the same schema, so a check-in interval past its maximum fails in the browser on blur, and a value the browser cannot judge (a UDS host it cannot reach) comes back as a 422 whose pointer /uds_db/host lands on the same field.
Changed: the file is plain. A leaf holds its value and nothing else; the ten metadata keys every node carried move into the schema shipped with the package. An administrator reads and edits the file as any Unix config, and cannot edit a rule.
Changed: both sides validate. AdminConfig and the setup page wrote whatever was typed; the routes deep-merged and wrote the file. Now the page runs every value through the schema on blur and on Update, and the route refuses with 422 and pointers before the merge.
Unchanged: the sections and foldable subsections, the navbar search over labels and keys, the password reveal, the SSL upload on upload fields, the secret masking on read and its restore on write, Update and Restart.

Tabs carry the state: a tab with any failing value is marked danger, a tab with none success, as the setup page does today; the summary lists every failing value of every tab so nothing hides behind an unvisited one.
Changed: dependsOn/showWhen is the schema's, not code's. The SQLite path replacing the SQL block was a special case in the setup page; now the host, port, user and password of the connection carry dependsOn: database_type, showWhen: [mysql] and the storage path showWhen: [sqlite], and the page only follows the schema.
Changed: enum is enforced. A select's value must be one of its enum on both sides; a hand-edited file carrying another word stops the UI backend at boot with the pointer.
The messages come from validation.<rule> with the field's title and bounds interpolated, the same keys the validation contract's forms use.

What the UI does with the answer

StatusSurface 422each errors[] pointer is a field path; the error paints there and in the summary; a rule outside the schema's vocabulary (reachable, writable) is one of the validation contract's named rules and paints from validation.reachable with the field's title; the host's detail is never shown 200the success card, the file re-read; a warning card "Restart the server to apply" when requiresRestart is true elseone danger card, the values kept
The file is what an administrator sees in a pager or a diff: values only, in the UI backend's own comments and order, 0600, owned by the service user; the schema never sits in /etc.
The schema is what the package owns: rules, titles, hints, order, restart flags, defaults; an upgrade replaces it with the release, and the UI backend answers it as JSON at GET /api/config/<name>/schema to any admin, since it carries no value.
A free subtree (the VDI pools overrides) is a type: object the schema marks with the UI backend's own x- annotation; the page does not draw it, the route still checks the types it declares.
