STARTcloud Universal Config

The picture of the Universal Config Contract; where the two disagree, the contract's text wins. Every backend keeps its settings in plain YAML files an administrator can read and edit, api_listen_port_encrypted: 443, and ships beside its code one schema per file that says what every value is, what it may be, how it is drawn and whether changing it needs a restart. The schema is the validation contract's rule set, JSON Schema 2020-12 keywords, so the admin page, the setup page and the write route evaluate one document and refuse a bad value the same way with the same body. One environment variable, CONFIG_DIR, no more; which config directory exists chooses the environment. There is no secrets handling: every value travels in the clear and writeOnly is the form's reveal hint alone. The first frame is live on BoxVault's app file, the contract's own example: set the HTTPS port past its maximum, clear the origin and press Update, then let the UI backend answer 422 for a value the browser could not know was wrong, and 200 with the restart card fed by restart-status.

a yellow note marks what this design changed against the apps as they were before it
Live — BoxVault's Configuration tab: app.config.yaml drawn from its schema, the tab labelled by the schema's root title, validated on blur and on Update, the PUT's 422 painted by pointer, the restart badge from requiresRestart, the restart card from restart-status
What this frame proves. Two documents, one form: the values come from GET /api/config/app, the labels, hints, types, bounds and enums from GET /api/config/app/schema, and the route evaluates the same schema, so an HTTPS port past its maximum fails in the browser on blur, and a value the browser cannot judge (a log directory the service user cannot write) comes back as a 422 whose writable entry carries params: { "user": "boxvault" } and paints from validation.writable; a pointer that names no field goes to the summary alone.
Changed: the file is plain. A leaf holds its value and nothing else; the ten metadata keys every node carried move into the schema shipped with the package. An administrator reads and edits the file as any Unix config, and cannot edit a rule.
Changed: both sides validate. AdminConfig and the setup page wrote whatever was typed; the routes deep-merged and wrote the file. Now the page runs every value through the schema on blur and on Update, and the route refuses with 422 and pointers before the merge.
Unchanged: the sections and foldable subsections, the navbar search over titles and keys, the password reveal, Update and Restart.
Changed: no secrets handling. writeOnly values were masked as ******** on read, the mask or a blank on write keeping the stored value. Now every value is in the clear in the file, on read and on write; writeOnly only hides the characters in the form, a password input with a reveal button, the raw value shown on click; the evaluator's SECRET_MASK and keepsSecret go.
Changed: default is drawn, never written. The value a missing key takes in memory at load is the placeholder of an empty text or numeric control and the hint Default: <value> after the description of a boolean or an enum, the control staying unset until the administrator sets it; no route, migration or boot step writes it into the file.

The gate is setup_complete: GET /api/setup/status answers { "setup_complete": true } exactly when setup.token does not exist; then the page draws setup.complete with one link, to /login on a backend with accounts and to / otherwise, and no token card and no tabs.
Changed: the verify answer. POST /api/setup/verify-token answers 204 on a constant-time match and hands nothing back; the browser keeps the token it sent as the bearer of every later setup call; 403 forbidden otherwise, painted on the token field; 404 not-found when setup is complete.
The token follows the first-boot pattern of Jenkins and Grafana: postinst creates an empty setup.token on first install, load fills it with 64 hex characters and logs its path, and the PUT /api/setup that succeeds deletes it.

What the UI does with the answer

StatusSurface 422each errors[] pointer is into the body as sent; the error paints on the field the pointer names and in the summary; a rule the schema cannot express (writable with params: { user }, reachable with params: { host, port }) is code on the route and paints from validation.<rule> with the field's title; a pointer that names no field goes to the summary alone; the host's detail is never shown 200the UI's own success card configManager.updateSuccess, never the server's message; the file re-read; restart-status re-read and the restart card drawn from it, listing each entry's title and reason until POST /api/config/restart answers 202; the editor never draws the PUT's own list elseone danger card, the values kept
The file is what an administrator sees in a pager or a diff: values only, in the UI backend's own comments and order, 0600, owned by the service user; the schema never sits in /etc.
The schema is what the package owns: rules, titles, hints, order, restart flags, defaults; an upgrade replaces it with the release, and the UI backend answers it as JSON at GET /api/config/<name>/schema to any admin, since it carries no value.
A free subtree is a type: object with neither properties nor additionalProperties: not drawn, not evaluated and not walked for unknown keys; a per-pool or per-site subtree the editor draws gains an item schema and becomes a map.
